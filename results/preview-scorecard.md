# ktServe preview scope and performance

The published release is [ktServe 0.2.0-preview.3](https://github.com/christian-draeger/kotlin-native-perf-lab/releases/tag/v0.2.0-preview.3). Use the [standalone library or checkout examples](../README.md#try-ktserve) with the matching platform. Linux uses one level-triggered epoll loop by default, Apple Silicon macOS uses kqueue, and the JVM uses NIO. Ktor and Spring Boot WebFlux have opt-in integrations for the documented HTTP/1.x surface. The guides describe their compatibility limits. [Transport contract](../components/ktserve/TRANSPORT.md) · [Ktor engine](../components/ktserve/integrations/ktor/README.md) · [Spring Boot WebFlux](../components/ktserve/integrations/spring-boot-starter/README.md)

The experiments below refer to the measured source revisions in their artifacts. The preview scope is functional compatibility and reproducible diagnostics. Production performance claims and default changes require the qualification below.

## Performance evidence

The four standalone implementations completed 48 mixed-application trials on GitHub-hosted x86_64 and ARM64, with zero measured response failures or dropped arrivals. Each architecture used a shared VM with disjoint logical CPU affinity for server and load. The table shows the medians of three trials per cell at 800 offered requests/s. A 50 ms gap between download chunks dominates the overall p99. The dashboard shows per-operation data for the wait, catalog, uploads, downloads and small JSON. [Mix details and raw trials](https://github.com/christian-draeger/kotlin-native-perf-lab/issues/114#issuecomment-7142891696) · [Dashboard](https://christian-draeger.github.io/kotlin-native-perf-lab/#integration-benchmarks)

| Linux | ktServe / Axum p99, ms | ktServe / Axum CPU s/million | ktServe / Axum peak RSS, MiB |
| --- | ---: | ---: | ---: |
| x86_64 | 52.011 / 51.730 | 139.82 / 87.41 | 22.9 / 9.1 |
| ARM64 | 51.755 / 51.606 | 94.86 / 52.43 | 21.6 / 8.5 |

The earlier expanded run reached 67–81% of Axum throughput on the three x86_64 endpoints and 66–83% on ARM64 with the one-worker configuration. Record the individual endpoints and their runner CPUs when drawing comparisons. Peak RSS and p99 differ with the application and the achieved load. ## Qualification for a performance claim

Use the [two-host protocol](../BENCHMARK_PROTOCOL.md#run-with-a-separate-load-machine) on dedicated native systems and qualify one architecture at a time. Declare the release revisions, equivalent workloads, protocol, CPU budgets, connection limits, rates, latency objectives and allowed error/drop rates before collecting scored data. Verify response parity, validate warm-up and generator headroom, and run at least five valid paired repetitions per cell. Retain invalid data with its reason. Archive settings, binaries, raw samples and cost and memory metrics.

For `/health`, `/json`, `/users/123` and `/catalog/123`, measure throughput separately from fixed-arrival latency. Use the same repeatable load levels and verify comparable delivered successful load for p99 and CPU. Evaluate the application mix as a separate series, including the predeclared 100 ms p99 and zero measured failures and drops where this pilot target applies. Keep direct HTTP/1.1, TLS ingress and HTTP/2 in separate comparisons.

For a parity claim on a workload, require at least 90% of Axum's measured successful throughput in the capacity run and at most 110% of its p99 and CPU cost at equal successful load. Compare medians across matched trials and report the range of paired ratios, peak RSS and end-of-window RSS. If a paired range crosses a limit, treat the result as inconclusive and investigate the dispersion. Establish any regression tolerance on the controlled hardware before applying it to releases. Hosted CI can validate behavior, delivered load and repeatability of the harness and flag directional changes. [Research criteria and limits](performance-research.md#measurement-and-decisions)

The parity gate is unqualified. Server and load generator shared hardware in the available measurements. The dedicated-host run and scored regression tolerance are deferred until the necessary hosts are available. [Qualification requirements and rehearsals](https://github.com/christian-draeger/kotlin-native-perf-lab/issues/16) · [Performance gate](https://github.com/christian-draeger/kotlin-native-perf-lab/issues/21)
